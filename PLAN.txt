  [B] PERFORMANCE (BLOQUEADOR CRÍTICO)
  ────────────────────────────────────
  ✅  Incremental layout — dirty flags por nó (não recomputar tudo a cada frame)
         ✅ DOM: NodeDirtyFlags (STYLE|LAYOUT|CHILDREN|SUBTREE) + mark_dirty() propagando p/ ancestrais
         ✅ Engine: build_layout_tree() consulta dirty flags (L831-856):
            • Nó limpo + sem descendentes sujos → pula subárvore inteira (cache node_to_taffy)

         ✅ recompute_dirty_styles() skipa quando zero nós têm flag STYLE
         ✅ recompute_layout() reseta todos os flags p/ NONE após layout (L630-633)
         ✅ styles_dirty (AtomicBool) + per-node flags consumidos em ambos os caminhos
  ✅  Style sharing cache (elementos com mesmo seletor compartilham estilo)
         ✅ HashMap<u64, ComputedStyle> em Stylesheet.style_sharing_cache (Arc<RwLock>)

            contexto de siblings (+ e ~), cadeia completa de ancestrais, e ambiente (vw/vh/color_scheme)
         ✅ calculate_style() faz lookup antes de calcular; insert após computar
         ✅ clear_cache() chamado em layout() quando viewport muda
  ✅  Paint invalidation inteligente (repintar apenas região modificada)
         ✅ InvalidationManager com dirty_rects + merge heurístico (union se área ≤ 1.5×; coalesce se >20 rects)
         ✅ Detecção por mudança de estilo (old != computed → add_dirty_rect expandido +20px)
         ✅ Detecção por mudança de geometria (previous_geometries vs nova posição/tamanho → invalida antigo + novo)
         ✅ Renderer: framebuffer persistente, clear seletivo só nas regiões sujas, skip primitivas fora de dirty_rects
         ✅ bridge.rs: return early sem repaint se dirty_rects vazio
  ✅  Virtual Scrolling / Culling (não renderizar elementos fora do viewport)

─── FASE JIT-2: TYPE SPECIALIZATION (Meses 4-6) ──────────────────────────────────

  Objetivo: Type feedback + Tier 2 com especialização de tipos.

  [x]  2.1  Type Feedback Collector
             → Inline Cache (IC) slots em cada operação (add, get_prop, call)
             → Registrar tipos observados: int32, float64, string, object, array
             → Estados: uninitialized → monomorphic → polymorphic → megamorphic
  [x]  2.2  Type Specialization no Tier 2
             → Se IC diz add(int32, int32) 100% do tempo:
               gerar instrução nativa IADD (CPU integer add) + overflow guard
             → Se IC diz add(float64, float64):
               gerar FADD (FPU add) direto, sem boxing
             → Se IC diz get_prop monomorphic (shape/hidden class conhecida):
               gerar load direto por offset de memória (elimina hash lookup)
  [x]  2.3  Hidden Classes / Shapes
             → Cada objeto JS recebe um Shape ID (hash da estrutura {keys+order})
             → Transições de shape formam uma árvore (shape tree)
             → JIT usa shape para acesso O(1) a propriedades por offset
  [x]  2.4  Guards e Deoptimization v1
             → Inserir type guards antes de código especializado
             → Se guard falhar em runtime: bailout → voltar para Tier 0
             → Safepoint map: para cada instrução JIT, saber onde estão os valores
               no stack frame para reconstruir o frame do interpretador
  [x]  2.5  On-Stack Replacement (OSR) — tier-up dentro de loops
             → Se um loop longo está rodando no Tier 0, compilar o loop body
               para Tier 2 e transferir a execução mid-loop para código nativo
  [x]  2.6  Builtins rápidos: Math.*, Array.push/pop, String.charAt, JSON.parse
             → Implementar em Rust puro com chamada direta (sem passa pelo JS)
  [x]  2.7  Testes: type specialization correctness
             → Testar deopt: função que muda tipos no meio da execução
             → Benchmark: Fibonacci, N-Body, Richards, DeltaBlue

  Entregável: Hot paths com tipos estáveis rodam em velocidade próxima a C/Rust.
  Speedup estimado: 15-30x sobre QuickJS puro. ~60-70% do V8.

─── FASE JIT-3: OTIMIZAÇÕES AVANÇADAS (Meses 7-10) ───────────────────────────────

  Objetivo: Alcançar/superar performance do V8 em benchmarks.

  [x]  3.1  Function Inlining ✅ (2026-03-22)
             → Inline funções pequenas (≤50 AIR ops) em call sites monomorphic
             → Inlining budget: máximo 3 níveis de profundidade por default
             → Implementado em tier2_compiler.rs: inline_air_function() + guard de
               identidade do callee + propagação de depth; 65/65 testes passando
  [x]  3.2  Loop Optimizations ✅ (2026-03-22)
             → Loop Invariant Code Motion (LICM): mover computações constantes
               para fora do loop
             → Loop Unrolling: desenrolar loops pequenos (≤8 iterações)
             → Strength Reduction: multiplicação → shift quando possível
  [x]  3.3  Escape Analysis
             → Objetos que não escapam da função → alocar no stack (não no heap) ✅
             → Scalar Replacement: substituir objeto por variáveis individuais ✅
             → Elimina pressão no GC para objetos temporários ✅
  [ ]  3.4  Dead Code Elimination + Constant Folding
             → Remover código inalcançável após inlining
             → Avaliar expressões constantes em compile time
  [ ]  3.5  Range Analysis e Bounds Check Elimination
             → Provar que índices de array estão sempre em bounds
             → Eliminar verificações de bounds em loops numéricos
  [ ]  3.6  Allocation Sinking
             → Postergar alocações de objetos até o ponto onde são necessários
             → Eliminar alocações em branches não tomados
  [ ]  3.7  SIMD Auto-vectorization (via Cranelift)
             → Array.map com operações numéricas → SSE/AVX em x86, NEON em ARM
  [ ]  3.8  RegExp JIT
             → Compilar expressões regulares diretamente para código de máquina
             → Usar o crate `regex` do Rust como backend (já é otimizado com SIMD)

  Entregável: Performance competitiva com V8 TurboFan em benchmarks padrão.
  Speedup estimado: 50-100x sobre QuickJS. ~80-100% do V8.

─── FASE JIT-4: GARBAGE COLLECTOR (Meses 8-12, paralelo à Fase 3) ────────────────

  Objetivo: GC geracional concorrente que não cause pausas visíveis (< 1ms).

  [ ]  4.1  Heap Layout
             → Young Generation (Nursery): 4-8 MB, semi-space copying
             → Old Generation (Tenured): Mark-Compact, crescimento dinâmico
             → Large Object Space: objetos >8KB direto no Old Gen
  [ ]  4.2  Young Gen — Semi-Space Copying Collector
             → Dois semi-spaces: from-space e to-space
             → Alocação: bump pointer (ultra rápido, 1 instrução)
             → Collection: copiar sobreviventes de from→to, swap spaces
             → Promoção: objetos que sobrevivem N coletas → Old Gen
  [ ]  4.3  Old Gen — Mark-Compact Collector
             → Tri-color marking (white/gray/black) para GC incremental
             → Compactação para eliminar fragmentação
             → Pode rodar em background thread (concurrent marking)
  [ ]  4.4  Write Barriers
             → Inserir barriers no código JIT: quando Old Gen aponta para Young Gen
             → Remembered Set: lista de ponteiros inter-geracionais
  [ ]  4.5  Safepoints no JIT Code
             → Cada ponto de GC no código nativo deve ter metadata:
               "quais registradores contêm ponteiros para o heap?"
             → Stack maps gerados pelo Cranelift
  [ ]  4.6  GC Concorrente
             → Marking phase em thread separada (concurrent marking)
             → Sweep/compact em pausas incrementais (≤1ms cada)
             → Write barrier Dijkstra-style para manter invariantes
  [ ]  4.7  GC Handshake com o QuickJS
             → QuickJS tem seu próprio GC (reference counting + cycle detector)
             → Bridge: quando JIT object é passado para QuickJS, criar ref handle
             → Quando QuickJS object entra no JIT heap, criar weak reference

  Entregável: GC que permite zero jank visual (sem pausas >1ms durante animação).

─── FASE JIT-5: DOM FAST PATH (Meses 11-14) ──────────────────────────────────────

  Objetivo: Integração JIT ↔ AceDOM sem overhead de FFI.

  [ ]  5.1  DOM Fast Path — acesso direto ao AceDOM sem cruzar ponte FFI
             → getElementById/querySelector: hash lookup direto no DomTree Rust
             → setAttribute/textContent: write direto na memória do DOM node
             → Elimina: JS → QuickJS → FFI → Rust (4 hops) → vira JS JIT → Rust (1 hop)
  [ ]  5.2  Layout Invalidation Tracking no JIT
             → JIT sabe quais nós DOM foram modificados → dirty flags automáticos
             → Batch DOM writes: acumular modificações, aplicar antes do próximo frame
  [ ]  5.3  Event Dispatch Otimizado
             → Event listeners compilados pelo JIT → dispatch direto sem interpretador
             → Inline listener code em hot paths (ex: scroll handlers)
  [ ]  5.4  Style Recalc Fast Path
             → Se JIT muda className/style → recalcular apenas subárvore afetada
             → Integração direta com o Stylesheet cache (style_sharing_cache)

  Entregável: Manipulação de DOM mais rápida que QUALQUER outro browser,
  porque não há barreira de linguagem (Rust JIT → Rust DOM = mesma memória).
  ESTA É A VANTAGEM COMPETITIVA QUE O V8/BLINK NUNCA TERÃO.

  Com equipe de 3 devs JIT:   ~6-8 meses

  LOC estimado: ~25.000 - 40.000 linhas de Rust puro.

  → V8 TurboFan: ~500.000 LOC C++ (15+ anos, 50+ engenheiros)

  → HermeJS (Meta/React Native): ~80.000 LOC C++ (JIT recente)

                          💡  PRINCÍPIOS DO PROJETO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. 🎯  BROWSER REAL, NÃO EXPERIMENTAL
     O Albedo é um browser de produção. Cada decisão deve considerar o impacto
     para usuários reais navegando na web real.

  2. 🦀  RUST-FIRST
     Escrito inteiramente em Rust. A segurança de memória e performance são
     vantagens competitivas reais sobre browsers escritos em C++.

  3. ⚡  PERFORMANCE É FEATURE
     Um browser lento é um browser ruim. Incremental layout, GPU compositing
     e rendering eficiente são tão importantes quanto novas APIs.

  4. 🔐  SEGURANÇA É INEGOCIÁVEL
     Sandboxing, site isolation, SRI e validação de TLS são requisitos, não extras.
     O browser toca na internet aberta — segurança é prioridade máxima.

  5. 🌐  COMPATIBILIDADE WEB ACIMA DE TUDO
     Se um site funciona no Firefox, deve funcionar no Albedo. A spec W3C é
     a referência. O objetivo é passar nos web-platform-tests (WPT).

  6. 🧪  TESTAR TUDO — E TESTAR VERDADEIRAMENTE
     Cada feature marcada como ✅ precisa de testes que provam a funcionalidade.
     Stubs com API surface não contam como implementados.
     Status honesto > ilusão de progresso.

  7. 📦  SHIPABLE MATTERS
     Build system, packaging e auto-update são parte do produto, não afterthought.
     Um browser que não instala facilmente não existe para o usuário final.

  8. 📊  PLANO COMO DOCUMENTO VIVO
     O PLAN.txt deve refletir a realidade do código, não aspirações.
     Após cada sessão: atualizar status, data e métricas.
     Contar LOC: find src -name "*.rs" | xargs wc -l | tail -1

  🚀  Albedo tem ~15.700 linhas de Rust, 30+ Web APIs, DOM funcional com testes,
      CSS engine com 100+ propriedades e JS runtime com QuickJS.
      A fundação está pronta. Agora é hora de transformá-la num browser real.

  ⚠️  PRÓXIMOS 3 PASSOS MAIS IMPACTANTES (auditoria 2026-02-26):
      1. Virtual scrolling / culling          → maior bloqueador restante para sites reais
      2. TextEncoder / TextDecoder            → ~100 linhas, desbloqueia frameworks
      3. ES Modules (import/export)           → sem isso, zero framework moderno funciona
