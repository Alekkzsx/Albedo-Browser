        ✅ Subframe engine factory with DOM isolation (AceEngine::create_subframe_engine)
        ✅ Iframe layout as leaf nodes (build_layout_tree treats as leaf like SVG)
        ✅ Iframe recursive rendering (render_visual extracts subframe primitives, adjusts coords)
        ✅ Separate JS runtime per iframe with parent/top references (runtime/core/init.rs)
        ✅ Same-origin policy enforcement for cross-frame access
        ✅ X-Frame-Options header validation (DENY, SAMEORIGIN)
        ✅ window.parent / window.top / window.frameElement references setup
        ✅ srcdoc attribute support + dynamic src loading
        ✅ IFrameBinding class with origin normalization
        ✅ Element intersection detection across iframe boundaries
        ⚠️  Lacks: contentWindow/contentDocument cross-context value marshalling (returns null)
        ⚠️  Lacks: postMessage / MessageEvent for iframe communication
        ⚠️  Lacks: nested iframe support (only 1 level deep verified)
  🟡  Web Workers — Estrutura sem execução real em thread separada
  🟡  Range e Selection — Stubs sem operações reais
  ✅  Element geometry (clientWidth, scrollTop, offsetHeight, etc.) reais
        ✅  clientWidth / clientHeight calculados (consideram borders/padding)
        ✅  scrollTop / scrollLeft implementados e mutáveis (estado por elemento)
        ✅  scrollWidth / scrollHeight medem a área de overflow vs container
  🟡  IntersectionObserver / ResizeObserver — Funcionais mas sem integração real
      com layout (não disparam baseado em posição/tamanho real dos elementos)
  ✅  HTTP/3 / QUIC — Implementado com Quinn + H3
        ✅ Http3Client com pooling de conexões QUIC (reusa por host)
        ✅ Endpoint QUIC com TLS 1.3 via rustls (native certificates)
        ✅ Timeouts: inicial 15s, idle 30s, keep-alive 5s
        ✅ Fallback automático: HTTP/3 (500ms) → HTTP/2 → HTTP/1.1
        ✅ Cache suporte HTTP/3 por host (evita retentativas)
        ✅ Cleanup automático idle connections (>60s)
        ✅ Testes unitários completos em tests/http3_tests.rs
  🟡  IndexedDB — Arquivo existe mas completamente vazio (rusqlite/sled necessário)
  🟡  GPU Rendering — wgpu estruturado mas rendering ainda 100% CPU via Slint
  🟡  Rendering de form widgets — Básico via Slint, mas sem estilização CSS real
  🟡  Table layout — Renderizado como Grid (funcional), mas sem rendering nativo
  🟡  Scroll — sem scrollbars, sem posicionamento real de scroll offset

                          💡  PRINCÍPIOS DO PROJETO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. 🎯  BROWSER REAL, NÃO EXPERIMENTAL
     O Albedo é um browser de produção. Cada decisão deve considerar o impacto
     para usuários reais navegando na web real.

  2. 🦀  RUST-FIRST
     Escrito inteiramente em Rust. A segurança de memória e performance do Rust
     são vantagens competitivas reais sobre browsers escritos em C++.

  3. ⚡  PERFORMANCE É FEATURE
     Um browser lento é um browser ruim. Incremental layout, GPU compositing
     e rendering eficiente são tão importantes quanto novas APIs.

  4. 🔐  SEGURANÇA É INEGOCIÁVEL
     Sandboxing, site isolation, SRI e validação de TLS são requisitos, não extras.
     O browser toca na internet aberta — segurança é prioridade máxima.

  5. 🌐  COMPATIBILIDADE WEB ACIMA DE TUDO
     Se um site funciona no Firefox, deve funcionar no Albedo. A spec W3C é
     a referência. O objetivo é passar nos web-platform-tests.

  6. 🧪  TESTAR TUDO
     Cada feature nova precisa de testes unitários. CI roda a cada commit.
     Fuzzing e benchmark regression previnem regressões silenciosas.

  7. 📦  SHIPABLE MATTERS
     Build system, packaging e auto-update são parte do produto, não afterthought.
     Um browser que não instala facilmente não existe para o usuário final.
